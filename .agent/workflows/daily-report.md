# سير عمل التقرير اليومي (Daily Report Workflow) - آمر تم

عند طلب المستخدم للتقرير اليومي أو استخدام الأمر `/daily-report` قم باتباع هذه القواعد الصارمة:

1. **الأسلوب والكتابة**:
   - اكتب بأسلوب بشري طبيعي (Human-like). تجنب العبارات النمطية للذكاء الاصطناعي.
   - استخدم لغة عربية مهنية ولكن بسيطة يفهمها غير المتخصصين.
   - ركز فقط على **أعمال المشروع والتطويرات**. لا تذكر ملفات القواعد (`.mdc`) أو التغييرات التقنية البحتة التي لا تهم المستخدم النهائي إلا إذا كانت جزءاً من ميزة.
   - اختصر المشكلات التقنية المعقدة إلى جمل بسيطة (مثلاً: "إصلاح مشكلة في إرسال الرسائل" بدلاً من "تحديث الـ DTO والـ Middleware").

2. **حالة "لا يوجد مهام"**:
   - إذا لم يتم إنجاز مهام في اليوم المطلوب، اكتب البيانات الأساسية للتقرير (التاريخ، اليوم، المشروع) ثم اكتب "لا يوجد مهام" بوضوح.

3. **تنسيق التقرير**:
   - التزم بالتنسيق التالي حرفياً:

تقرير يومي - [اليوم], [التاريخ]

👤 الأسم: [الأسم]

✅ الإنجازات:
* [إنجاز 1]
* [إنجاز 2]

⚠️ التحديات:
[التحدي أو "لا يوجد"]

📅 خطة الغد:
[خطة اليوم التالي]

4. **جمع المعلومات وتحليل الإنجازات**:
   - الاسم: هشام قاسم الصغير
   - المشروع: آمر تم - قطاع الأعمال (AMRTM Business)
   - **تحليل GitHub**: يجب عليك الوصول إلى GitHub وتحليل نشاط المستخدم `hisham-cmd` لنفس يوم التقرير.
    - ركز على المستودع: `amrtm_business` (مشروع Laravel متكامل).
   - **كيفية جمع المعلومات من GitHub بالتفصيل**:
     a. استخدم `github_list_commits` للمستودع للحصول على قائمة commits (بدون فلترة بالتاريخ).
     b. اقرأ تاريخ كل commit من حقل `commit.author.date` و صفية فقط commits التي تخص يوم التقرير.
     c. **مهم: مراعاة فارق التوقيت (Timezone)** - commits ذات التاريخ UTC لليوم السابق بعد الساعة 21:00 قد تكون في يوم التقرير بتوقيت السعودية (UTC+3). مثلاً: commit بتاريخ `2026-05-21T21:00:30Z` يوافق `2026-05-22T00:00:30` في السعودية. وسّع نطاق البحث ليشمل commits من 21:00 UTC من اليوم السابق.
     d. **للحصول على تفاصيل الملفات المتغيرة في كل commit**، استخدم GitHub API المباشر: `curl -s "https://api.github.com/repos/hisham-cmd/amrtm_business/commits/{SHA}"` واستخرج قائمة `files` التي تحتوي على `filename`, `status`, `additions`, `deletions`.
     e. **للحصول على الـ diff الفعلي**، استخدم الـ header: `Accept: application/vnd.github.v3.diff` مع نفس رابط commit API أعلاه.
     f. قم بتلخيص التغييرات إلى إنجازات وظيفية واضحة للمستخدم (ليست مجرد تكرار لرسائل الـ commits).
       - **ملاحظة بديلة (في حال تعذر الوصول لـ GitHub)**: إذا واجهت مشاكل في صلاحيات الوصول لـ GitHub عبر الـ MCP، يمكنك استخدام سطر الأوامر لتشغيل `git log` مباشرة في المجلد المحلي للمستودع (`amrtm_business`) لجمع قائمة الـ commits وتحليل تفاصيلها ليوم التقرير.
      - **ملاحظة (أجهزة جديدة)**: على الجهاز الجديد قد لا يتعرف الطرفية على `git` أو `php` أو `node` رغم تثبيتها بسبب PATH قديم في الجلسة؛ قبل تشغيل أي أوامر حدّث PATH من متغيرات النظام (Machine + User) ثم أعد المحاولة.
      - **ملاحظة: إذا لم يكن للمستودع أي commits بعد**، استخدم git log داخل المجلد المحلي أولاً. إذا لم توجد commits، فهذا يعني أن المستودع لم يُرفع بعد ويمكن ذكره في التقرير كإنجاز معلق.
     - راجع أيضاً `task.md` والرسائل الأخيرة لضمان عدم فوات أي تفاصيل تمت خارج GitHub.
     - **راجع جلسة العمل الحالية (session messages)** قبل كتابة التقرير: قد يكون المستخدم قد ذكر إنجازات أو أخطاء أو تحديثات لم تُرفع بعد لـ GitHub. ادمج هذه المعلومات مع ما تجده من commits.
   - المسارات الثابتة للملفات:
     - ملف الـ workflow: `.agent/workflows/daily-report.md`
     - ملف المهام: `task.md`
     - مجلد التقارير: `.agent/reports/`

5. **إخراج التقرير**:
   - **دائماً** احفظ التقرير في ملف نصي قابل للنسخ:
   - المسار: `.agent/reports/daily-report-YYYY-MM-DD.txt`
   - استخدم التاريخ المطلوب للملف (مثال: `daily-report-2026-09-08.txt`)

6. **تحسين مستمر للـ workflow**:
   - في نهاية إنشاء التقرير، أضف أي تحسينات جديدة إلى هذا الملف (`daily-report.md`) إذا لاحظت أن المستخدم احتاج لتوضيح خطوة معينة أو إعادة تعليمات لم تكن موجودة من قبل.
   - هذا يضمن أن المستخدم لن يحتاج لذكر نفس التفاصيل مرة أخرى في المستقبل.

7. **طلب تقرير ليومين أو تقسيم مهام (مثل: "تقسيم وتوزيع المهام على تاريخ X و Y")**:
   - أنشئ ملف تقرير منفصل لكل يوم (`daily-report-YYYY-MM-DD.txt`).
   - اليوم الذي حدثت فيه الإنجازات فعلاً: اكتبها كإنجازات منجزة (من الـ commits والجلسة).
   - اليوم المستقبلي (لم يحدث بعد): اكتب المهام الموزعة عليه في قسم الإنجازات دون أي ملاحظات حول تأجيلها.
   - الافتراض المعتاد: أعمال اليوم الأول = "الآن" واليوم الثاني = "الخطة القادمة" ما لم يحدد المستخدم غير ذلك.

8. **تقرير مالك الشركة (DOCX) — غير تقني**:
   - عند طلب "تقرير المالك" أو تقرير DOCX بين تاريخين، شغّل سكربت التوليد الجاهز بدل كتابة التقرير يدوياً:
     - التشغيل التفاعلي: `run_owner_report.bat` (يسأل عن تاريخ من/إلى).
     - التشغيل المباشر: `python .agent/workflows/owner_report_generator.py --from YYYY-MM-DD --to YYYY-MM-DD`.
   - السكربت يجمع الـ commits من Git محلياً، ويترجمها بالكامل إلى العربية (لا وجود لأي مصطلح لاتيني في الوثيقة — عبر `EXACT_MAP` للتحديثات المعروفة وقاموس `TERM_DICT` لأي تحديث جديد)، ويفرض اتجاه يمين-إلى-يسار على كل فقرة ونص وجدول، بأرقام عربية (٠١٢٣) وتواريخ عربية (مثل: ١٣ سبتمبر ٢٠٢٦). ويولد ملفين معاً في `.agent/reports/`: `owner-report-YYYY-MM-DD.docx` و `owner-report-YYYY-MM-DD.pdf` (التحويل عبر Microsoft Word COM — يحتاج تثبيت Word فقط، وإن تعذر يُتخطى الـ PDF مع تحذير). التقرير يتضمن:
     - شعار الشركة (`public/images/new-logo1.png`) وهوية آمر تم (الأخضر الملكي #006C35) بنصوص عربية RTL.
     - ملخص تنفيذي + جدول مؤشرات + الإنجازات مصنفة حسب المجال + قسم الجودة والاستقرار + خاتمة موجهة للإدارة.
   - إن طلب المستخدم تعديل الصياغة بعد التوليد، عدّل السكربت نفسه (قاموس `TOPIC_MAP`/`TYPE_MAP`) ثم أعد التوليد — لا تعدّل ملفات DOCX يدوياً.

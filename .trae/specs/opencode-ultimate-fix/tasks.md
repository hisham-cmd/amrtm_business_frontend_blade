## Task 1: تحسين سكربت الصيانة التفاعلي `fix_opencode_cache.py`

**الأولوية:** عالية
**التبعيات:** لا يوجد

### الوصف
تحديث السكربت الحالي لإضافة خيارين جديدين [8] و [9]، وتحديث خريطة النماذج والدليل التشخيصي.

### الربط مع معايير القبول (ACs)
- FR-B1 → AC-R5 (خيار [9] يعمل نفس الإصلاح الشامل)
- FR-B2 → AC-Ru1 (إنشاء اختصارات سطح المكتب)
- FR-B3 / FR-B4 → الوضوح العام

### مهام فرعية
1.1. إضافة `_ACTIVE_PROVIDER` افتراضي إلى "zen" مع تعليق شرحي.
1.2. تحديث `_ctx_map` لتتضمن علامات ✅/⚠️/❌ بتاريخ الاختبار.
1.3. إضافة دالة مساعدة جديدة `create_desktop_shortcuts()` تنشئ ملفات BAT+VBS+دليل TXT على سطح المكتب.
1.4. إضافة دالة مساعدة جديدة `run_ultimate_fix_noninteractive()` تشغل نفس الخوارزمية في standalone_FIX_ALL بدون قائمة.
1.5. تحديث الدالة الرئيسية `run_menu()` لإضافة خيار [8] و [9].
1.6. تحديث الدليل التشخيصي `run_option_5_maintenance_guide()` مع إضافة قسم `free-models-per-day`.
1.7. تحديث جدول الملخص السريع للأسئلة الشائعة.

### متطلبات الاختبار (TRs)

#### قواعد (Rules)
- **TR-1.1:** `py_compile` على السكربت بعد التعديل ينجح بدون أخطاء.
- **TR-1.2:** تشغيل السكربت + إدخال "9" + "y" ينتج نسخة احتياطية + تقرير في مجلد التقارير.
- **TR-1.3:** تشغيل السكربت + إدخال "8" ينشئ الملفات الثلاثة على سطح المكتب.

#### مقاييس (Rubrics)
- **TR-1.4 سلوك القائمة (0-3):**
  - 0: الخيارات الجديدة غير موجودة
  - 1: موجودة لكن لا تعمل
  - 2: تعمل لكن لا توجد رسائل تأكيد واضحة
  - 3: تعمل + رسائل [OK] / [WARN] واضحة + ملخص في النهاية
  - **عتبة النجاح:** ≥ 2

## Task 2: إنشاء سكربت الإصلاح التلقائي المستقل `standalone_FIX_ALL.py`

**الأولوية:** عالية
**التبعيات:** Task 1 (يمكن البدء معه بشكل متوازٍ لكن الاعتماد المفاهيمي على مفاهيم Task 1)

### الوصف
سكربت بايثون مستقل (يعمل حتى لو لم يكن `fix_opencode_cache.py` موجودًا) ينفذ كافة خطوات الإصلاح تلقائيًا بدون أي قائمة أو مدخلات.

### الربط مع معايير القبول
- FR-A1 → A11 → AC-R1 و AC-R2
- NFR-1 / NFR-2 / NFR-3 / NFR-6 → الجودة العامة

### مهام فرعية
2.1. نسخ المنطق المشترك من `fix_opencode_cache.py` (الإعدادات الافتراضية _DEFAULTS، خريطة _ctx_map، دوال upsert_provider_into_cfg و delete_glob).
2.2. دوال جديدة خاصة بالسكربت:
     - `timestamp_str()` → لإنشاء أسماء ملفات بالطابع الزمني.
     - `create_backup_zip()` → أخذ نسخة ZIP احتياطية.
     - `ensure_report_dir()` → إنشاء مجلدات التقارير والنسخ الاحتياطي.
     - `select_best_provider()` → اختيار مزود الأمثل بهذه الأولوية: Zen → OpenRouter → Groq.
     - `apply_provider_models_and_settings()` → تعيين النماذج الأربعة + إعدادات compaction.
     - `clear_all_caches()` → مسح كاش شامل (NFR-6).
     - `generate_fix_report()` → كتابة تقرير TXT مفصل (FR-A9).
     - `rollback_from_backup()` → الاسترجاع في حالة الفشل (FR-A11).
2.3. دالة `main()`: تقرع وسيط `-y`، ثم تشغل الخطوات بترتيب: نسخ احتياطي → فحص JSON → تسجيل مزودين → اختيار مزود → تطبيق الإعدادات → مسح الكاش → تقرير.
2.4. دعم وسيط `--provider {zen|openrouter|groq}` للفرض يدوياً.

### متطلبات الاختبار (TRs)

#### قواعد (Rules)
- **TR-2.1:** `python standalone_FIX_ALL.py -y` يكتمل Exit Code 0.
- **TR-2.2:** بعد تشغيله، يوجد ملف `fix_report_*.txt` في مجلد التقارير، والملف غير فارغ (أكثر من 300 بايت).
- **TR-2.3:** يوجد ملف `opencode_backup_*.zip` صالح (يمكن فتحه كـ ZIP) في مجلد النسخ الاحتياطية.
- **TR-2.4:** `opencode.json` الناتج يكون صالح JSON، ومفتاح `model` يبدأ ببادئة المزود المختار (`opencode/` أو `openrouter/` أو `groq/`).
- **TR-2.5:** `python standalone_FIX_ALL.py --provider zen -y` يجبر المزود إلى Zen بغض النظر عن الفحوصات.
- **TR-2.6:** السكربت لا يستورد أي مكتبة غير stdlib (فحص نصي برمجيًا).

#### مقاييس (Rubrics)
- **TR-2.7 سرعة التنفيذ (0-3):**
  - 0: > 120 ثانية
  - 1: 60-120 ثانية
  - 2: 30-60 ثانية
  - 3: < 30 ثانية
  - **عتبة النجاح:** ≥ 2 (≤ 60 ثانية)
- **TR-2.8 جودة تقرير الإصلاح (0-3):**
  - 0: لا يوجد تقرير
  - 1: ذكر بسيط "تم الإصلاح"
  - 2: يذكر: المزود قبل/بعد، النماذج الأربعة بعد التعديل، مسار النسخة الاحتياطية.
  - 3: يذكر: وقت البدء/الانتهاء، المزود+النماذج قبل التعديل وبعده، حجم الكاش المحذوف بالبايتات (تقديري)، عدد الملفات المحذوفة، صلاحية JSON النهائية، توصيات بعد الإصلاح.
  - **عتبة النجاح:** ≥ 2

## Task 3: إنشاء ملفات التشغيل BAT + VBS + دليل TXT على سطح المكتب

**الأولوية:** عالية
**التبعيات:** Task 2 (تحتاج ملف standalone_FIX_ALL.py موجود لتشغيله)

### الوصف
ملفات سهلة الاستخدام للمستخدم النهائي.

### الربط مع معايير القبول
- FR-C1 / C2 / C3 → AC-R3 و AC-Ru1
- FR-D1 / D2 → AC-Ru1

### مهام فرعية
3.1. كتابة `إصلاح OpenCode - شغّل كمسؤول.bat`:
     - فحص صلاحيات المسؤول (net session >nul).
     - إن لم يكن مسؤول: تشغيل PowerShell Start-Process -Verb RunAs لإعادة تشغيل الـ BAT.
     - تعيين عنوان نافذة CMD، ولون الخلفية والأحرف (أزرق فاتح + أبيض).
     - تشغيل `python standalone_FIX_ALL.py -y`.
     - في النهاية: إظهار رسالة "اضغط أي مفتاح للخروج" + عرض ملف التقرير الأخير بـ notepad.
3.2. كتابة `إصلاح OpenCode - بدون نافذة.vbs`:
     - يستخدم `Shell.ShellExecute "runas"` لرفع الصلاحيات ثم تشغيل الـ BAT مع إخفاء النافذة.
3.3. كتابة `00_كيفية_الإصلاح_بنقرة_واحدة.txt`:
     - شرح موجز باللغة العربية لكل ملف، ومتى نستخدمه، وكيف نعرف أن الإصلاح نجح.
3.4. نسخ الملفات الثلاثة فعليًا إلى سطح المكتب عند تنفيذ Task 1 أو Task 3.

### متطلبات الاختبار (TRs)

#### قواعد (Rules)
- **TR-3.1:** الثلاثة ملفات موجودة في `~/Desktop/` بعد التنفيذ.
- **TR-3.2:** محتوى الـ BAT يحتوي سلسلة `runas` أو `Verb RunAs` أو `Start-Process` (يضمن طلب رفع الصلاحيات).
- **TR-3.3:** محتوى الـ VBS يحتوي سلسلة `ShellExecute` و `"runas"`.

#### مقاييس (Rubrics)
- **TR-3.4 وضوح أسماء الملفات (0-3):**
  - 0: أسماء عامة (fix.bat, run.vbs)
  - 1: أسماء واضحة لكن بالإنجليزية
  - 2: أسماء عربية واضحة
  - 3: أسماء عربية + بادئة رقمية للترتيب + شرح في نافذة الـ BAT
  - **عتبة النجاح:** ≥ 2

## Task 4: التحقق النهائي والاختبار المتكامل

**الأولوية:** متوسطة (ولكن إلزامية لاعتماد الحل)
**التبعيات:** Task 1 و Task 2 و Task 3 كلها مكتملة.

### الوصف
تشغيل دورة اختبار كاملة، والتحقق من صحة جميع المخرجات، ثم كتابة ملخص نهائي للمستخدم.

### مهام فرعية
4.1. `py_compile` لكلا السكربتين.
4.2. تشغيل `standalone_FIX_ALL.py -y` فعليًا وجمع المخرجات.
4.3. فتح ملف التقرير الناتج وتدقيق محتواه (TR-2.8).
4.4. فتح نسخة ZIP الاحتياطية وضمان صلاحيتها (TR-2.3).
4.5. فحص `opencode.json` الناتج للتأكد من صحة النماذج والمزود.
4.6. التحقق من وجود ملفات سطح المكتب الثلاثة.
4.7. كتابة سجل الأدلة النهائية.

### متطلبات الاختبار (TRs)

#### قواعد (Rules)
- **TR-4.1:** كل من TR-2.1, 2.2, 2.3, 2.4, 3.1 تحقق أرض الواقع.
- **TR-4.2:** لا يوجد أخطاء ملونة حمراء (FAIL) في مخرجات التنفيذ الفعلي.
- **TR-4.3:** السكربت لا يحذف مجلد `.config/opencode/mcp-daemon/servers` أو ملفات إعدادات MCP الحرجة (فقط السجلات والـ pid).

#### مقاييس (Rubrics)
- **TR-4.4 الثقة النهائية في الحل (0-3):**
  - 0: لم ينجح أي جزء
  - 1: نجح جزء واحد فقط
  - 2: نجحت جميع المهام لكن مع تحذيرات بسيطة
  - 3: نجح كل شيء بدون تحذيرات + تقارير مفصلة + تجربة سلسة
  - **عتبة النجاح:** ≥ 2
